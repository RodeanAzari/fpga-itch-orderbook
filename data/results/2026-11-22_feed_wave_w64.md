## Result

- All four packets go in back to back with the output always ready. The DUT's 133 records
  equal `model.moldudp64.FeedDecoder`'s, field by field, in order; the locate is learned
  from the R message in the first packet; never stale. The test fails otherwise, so the
  CSV is only written for a correct run.
- The shown packet (index 3: MoldUDP64 sequence 143, 47 messages, 1,466 bytes) is 184
  input words. The input waited (tready low) on 56 cycles, so the packet took 240 cycles
  to go in; its last record left 244 cycles after its first word.
- The 47 record types, `AAAADADADADAADDAAADADADAADADADADADADAADDADAADAD`, are the ones
  the ILA captured from the decoder on the board for the same packet.

## Interpretation

This is the Phase C waveform of buildplan §9: one packet splitting into messages across
bus words. In the input, a message starts in any lane (byte 22 of the packet, the first
message's type, is lane 6 of the third word). The deframer drops the 2-byte length prefixes
but leaves each message in the lanes it arrived in; the aligner moves each one to lane 0,
so the decoder takes every field from a fixed offset. It is simulation, not a capture: on
the board, the decoder runs at `DATA_W` 8 (the release build), and the 64-bit path's
hardware evidence is the injector and full-day runs (`2026-11-15_injector_board_w64.md`,
`2026-11-15_w64_full_day_board.md`).
